# CallFlow Companion Phase 4 — トラブルシューティング

作成日: 2026-07-22

| 状況 | 案内 |
|---|---|
| 「Codexで営業内容を解析」が表示されない | `NEXT_PUBLIC_CALL_ANALYSIS_ENABLED`が有効か確認。文字起こしが完了している必要がある |
| `not_authenticated`（Codexへのログインが必要です） | ターミナルで`codex login`を実行し、ChatGPTアカウントでログインする |
| `usage_limit_exceeded`（Codexの利用上限に達しています） | ChatGPTアカウントの利用上限が回復してから再試行する |
| `codex_unavailable`（Codexアプリサーバーを起動できませんでした） | `codex --version`でCLIが正しくインストールされているか確認。再起動を1回試みても失敗する場合は、Companionを再起動する必要がある（無限再起動はしない設計のため） |
| `invalid_output`（Codexからの応答を解析結果として解釈できませんでした） | Codex側の応答が2回ともJSON Schemaに適合しなかった場合に発生する。再試行で解消することが多い |
| `transcript_too_long`（文字起こしが長すぎるため解析できません） | 4万字を超える文字起こしは非対応。録音を分割するか、この制限が緩和されるバージョンを待つ |
| `transcription_not_found` / `transcription_not_ready` / `transcription_empty` | 参照元の文字起こしジョブが見つからない・未完了・空。文字起こしが完了してから解析を開始する |
| ジョブが`404`になる（存在しないはずのjobIdでもない） | Companionを再起動していないか確認。ジョブはメモリ上のみで保持され、Companion再起動・完了から10分経過（TTL）で失効する |
| キャンセルしたのに少し反応が遅い | `DELETE`は解析中断の指示を送った直後に応答するが、Codex側の実際の中断は非同期に進む。UI上は即座に「キャンセル済み」表示になり、待つ必要はない |
| 解析結果が保存されない・ページ再読み込みで消える | Phase 4の仕様どおり。「架電フォームへ反映」を押すまでは一切保存されない（意図的な設計） |
| 「架電フォームへ反映」を押しても担当者名が更新されない | 意図的な仕様。検出した担当者名はメモ内に参考情報として表示されるのみで、企業情報の担当者名は自動上書きしない |
| 温度感が反映されない | 「この温度感を企業情報に適用する」チェックボックスは既定でオフ。明示的にオンにしてから「架電フォームへ反映」を押す必要がある |
| 表示中の企業が変わったら録音・文字起こし・解析結果が消えた | 意図的な安全策（企業取り違え防止）。録音開始時と異なる企業を表示した状態では解析・反映のいずれもできない |
| 次回対応日の入力欄が空欄になる | Codexが返す日時形式（タイムゾーン付きISO 8601）をブラウザの日時入力欄向けに変換しているが、まれに変換に失敗する場合がある。手動で入力し直せば保存には影響しない |

## 付録: 開発時に発見・修正した既知の問題

開発中の自動テストで、以下2点を実際に発見・修正した（詳細は[callflow-analysis-phase4-review.md](./callflow-analysis-phase4-review.md)参照）。

1. **キャンセル中の書き込みでCompanion全体が落ちる可能性があった**: 解析キャンセル（`turn/interrupt`送信）とCompanion終了処理が競合するタイミングで、Codex子プロセスへの書き込みが失敗し、Node.jsの既定動作でCompanionプロセス全体が異常終了しうる状態だった。`stdin`/`stdout`/`stderr`それぞれに`'error'`リスナーを追加し、書き込み前に接続状態を確認するよう修正した。
2. **Codexプロセスの異常終了時、原因不明のエラーとして扱われていた**: Codexプロセスの起動失敗・タイムアウト・異常終了が、利用者には「Companion内部でエラーが発生しました」という原因不明のメッセージとして表示されていた。「Codexアプリサーバーを起動できませんでした」という具体的なメッセージに正しく分類されるよう修正した。
