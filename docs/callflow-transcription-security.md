# CallFlow Companion Phase 3B — セキュリティ設計まとめ

作成日: 2026-07-22
対象ブランチ: `feature/local-call-recorder-codex`

このドキュメントは、独立したセキュリティレビュー（Opus、`companion/src/transcription-*.ts`を対象に実施、詳細は[callflow-transcription-phase3-review.md](./callflow-transcription-phase3-review.md)参照）の結果を踏まえた、Phase 3B（ローカル文字起こし）のセキュリティ設計の要点である。

---

## 1. コマンド/引数インジェクション対策

- `child_process.spawn`は常にargv配列で呼び出し、`shell: true`・文字列結合によるコマンド構築・`eval`は一切使用しない
- ffmpeg/whisper-cliに渡すファイルパスは、すべてサーバー側`crypto.randomUUID()`由来の一時ファイル名（`temp-files.ts`）に限定される。リクエストヘッダー（企業名・録音ID等）がコマンドライン引数へ混入する経路は存在しない
- モデル名も`"base"|"small"`の2値の型で制約されており、任意文字列がコマンドラインへ渡ることはない

## 2. パストラバーサル対策

- `jobId`はMapのキーとしてのみ使用され、ファイルシステムパスの組み立てには一切使用しない
- `jobId`にスラッシュを含む場合は`400`で拒否。URLエンコードされたスラッシュ（`%2F`）を含む場合も、ルーティング上ただの不一致文字列として扱われ`404`になる（パス解釈をバイパスして意図しないリソースへ到達することはない）
- 一時ファイルの作成・削除は`temp-files.ts`の`isWithinTmpDir()`でtmpDir配下であることを常に検証する（Phase 2A以来の既存ガード、Phase 3Bでも同じ関数を再利用）

## 3. 認証・認可（ジョブの所有者確認）

- ジョブごとに、発行元のBearerトークンをSHA-256でハッシュ化した値を保持する（`pairing.ts`の`hashToken`と同一アルゴリズムを、`pairing.ts`自体は変更せず`transcription-jobs.ts`内で独立して算出）
- `getJob`/`cancelJob`は`crypto.timingSafeEqual`でハッシュを比較し、不一致の場合は`null`を返す→呼び出し側は`404`を返す（他人のジョブの**存在有無すら**判別できない設計）
- `POST /v1/transcriptions`は`isAuthorized()`（既存のBearerトークン検証）を通過して初めてジョブが作成される。ジョブ自体は「検証済みトークンのハッシュ」に紐づくため、認証をバイパスしてジョブを作ることはできない
- `GET`/`DELETE`についても、Origin未許可の場合は明示的に`403`で拒否する（POSTと同様の多層防御。従来はPOSTのみ明示チェックしていたが、レビュー指摘を受けてGET/DELETEにも統一した）

## 4. 情報漏洩対策

- エラーレスポンス・ログには、絶対パス・トークン・文字起こし全文が含まれないことを自動テストで確認済み（レスポンスJSONを文字列化して`/Users/`・`Bearer`等のパターンを含まないことを検証）
- サブプロセスの標準エラー出力（`stderrTail`）はデバッグ用に内部で保持するのみで、HTTPレスポンス・ログへは出力しない

## 5. リソース枯渇（DoS）対策

- 同時実行数1・待機キュー上限2（設定可能）。**アップロード受信中（`await`で音声を受け切るまでの間）も上限判定に含める**ようにしている。受信中はまだキューに積まれないため、これを判定に含めないと大量の同時リクエストで上限を回避できてしまう（レビューで指摘され修正済み）
- アップロードサイズ上限（既定100MB）は、`Content-Length`ヘッダーの偽装・省略に関わらず、実受信バイト数で強制する（既存の`/v1/audio`と共通の`audio-upload.ts`のロジック）
- 音声長上限（60分）はWAV変換後のファイルサイズから算出し、超過時は文字起こしを実行せず拒否する
- whisper-cli実行タイムアウトは音声長に比例した動的な値（実測real-time factor×安全係数、上下限クランプ付き）とし、極端に長い音声で無制限に処理が続くことを防ぐ
- サブプロセスの標準出力・標準エラー出力はバイト数上限（既定1MB）でキャップし、メモリ肥大化を防ぐ

## 6. プロセス終了・一時ファイルの確実な削除

- キャンセル・タイムアウト・Companion終了のいずれでも、ffmpeg/whisper-cliのプロセスグループ全体（子だけでなくその子孫プロセスも含む）へシグナルを送る。直接の子プロセスのPIDだけをシグナルすると孫プロセスが孤児化しうるため（Phase 3Aで実際に発見・修正した既知のクラス）
- 音声・WAV・JSONの3種類の一時ファイルは、成功・失敗・キャンセルいずれの経路でも削除を試みる。`process()`の自然完了と明示キャンセルが競合する場合でも、`job.finished`フラグにより一時ファイル削除ロジックが二重実行されないようにしている（多重実行自体は実害が少ないが、二重登録されたタイマーがCompanionプロセスの終了を妨げる副作用があったため、根本対策として実装した）
- 文字起こし結果（テキスト）はメモリ上のみで保持し、ディスクへは一切書き込まない。完了ジョブはTTL（既定10分）経過後にメモリから自動削除される

## 7. レビューで見つかり、修正済みの項目

| 重要度 | 内容 | 対応 |
|---|---|---|
| P2 | アップロード受信中の件数が同時実行/待機上限の判定に含まれておらず、大量の同時リクエストで上限を回避できた | 受信中件数を判定に含めるよう修正 |
| P3 | `temporaryFilesDeleted`が処理中でも`true`のまま初期化されており、削除済みでない音声を「削除済み」と誤って案内していた | `false`で初期化し、実削除後にのみ`true`にするよう修正 |
| P3 | GET/DELETEにPOSTと同じ明示的なOrigin検証が無かった（Bearer認証・プリフライトで実質的には保護されていたが、多層防御として不統一だった） | GET/DELETEにも明示的なOrigin検証を追加 |
| P3 | ffmpeg完了直後〜whisper起動までの間にキャンセルが割り込むと、削除済みWAVに対してwhisper-cliを起動しうる（実害は起動失敗のみ） | `job.finished`チェックを各フェーズの節目に追加 |

詳細な検出プロセス・信頼性レビューの指摘（別カテゴリ）は[callflow-transcription-phase3-review.md](./callflow-transcription-phase3-review.md)を参照。

## 8. Phase 3Bのセキュリティ境界外（意図的に対象外）

- Companion自体はローカルの信頼された利用者（同一Mac上のブラウザ）を前提としたツールであり、リモートからの到達は`127.0.0.1`固定bindにより構造的に不可能
- ペアリング・トークンの発行・失効ロジック自体（Phase 2A/2Bで既にレビュー済み）は本Phaseの変更対象外
