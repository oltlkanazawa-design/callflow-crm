# Phase 4（Codex営業通話解析）レビュー記録

作成日: 2026-07-22
対象ブランチ: `feature/local-call-recorder-codex`

このセッションでは、Claude Code（Sonnet 5）が実装者として作業し、設計・セキュリティ・信頼性・最終ゲートの4段階のレビューを、独立したClaude Codeサブエージェント（`Agent`ツール、`subagent_type: general-purpose`、`model: "opus"`で起動。このセッションの実行環境では`model: "opus"`はOpus 4.8（`claude-opus-4-8`）に解決される）を、各段階ごとに毎回新規のインスタンスとして使用して実施した。すべて読み取り専用（コード編集権限なし）で実行し、指摘の修正は実装者（本セッションのメインエージェント）が行った。

Phase 3で判明した制約（プロジェクト固有のサブエージェント定義`.claude/agents/*.md`は稼働中のセッションではホットリロードされない）を踏まえ、役割ごとのレビュー観点・手順は`general-purpose`エージェントへのプロンプトに直接埋め込む形で実施した。

## 1. 設計レビュー（実装前）

実装前の計画書（RPCの実プロトコル調査結果・既存コードとの整合ポイントを含む）を、独立したOpusレビュアーへ提示して実施。

**判定: REVISE（狭い範囲での指摘）**

検出事項:
- P1: turnあたりの明示的なタイムアウトが計画に明記されておらず、同時実行数1の制約下でハングしたturnがキュー全体を永久に塞ぐ可能性
- P2×4: turn/interruptのターンID未確定時のキャンセル競合、複数turnにまたがるthread/readでの対象turn選定ルール未定義、長期生存するJSON-RPCプロセス特有のペンディングリクエスト管理・シャットダウン順序の詳細不足、機密性の担保が「読み取り専用サンドボックス」ではなく「ツール未提供」自体にある点の明文化不足
- P3×3: 子プロセスへの環境変数を許可リスト化すべき、企業ID整合性チェックがCompanion側では検証されない（ブラウザ側のみ）ことの明記、既存`TranscriptAnalysis`型との差分の意図的な扱い

P0は無し。指摘はすべて実装時に反映済み（turnタイムアウトの実装、環境変数許可リスト化、企業ID整合性がブラウザ側のみの検証であることの文書化等）。

## 2. セキュリティレビュー

対象: `companion/src/{codex-app-server,codex-analysis,analysis-schema,analysis-prompt,analysis-jobs,analysis-routes}.ts`、`companion/src/server.ts`の差分、`src/lib/companion-client.ts`、`src/components/{call-recorder,callflow-app}.tsx`。

**判定: SHIP**（P0・P1なし）

検出事項（いずれもP3、非ブロッキング）:
- 解析の同意ダイアログ文言が、文字起こしがOpenAIへ実際に送信される点を明示していない（ただし、この文言はユーザー自身が指定した文言をそのまま使用しており、変更していない。OpenAI送信の事実自体はドキュメントに明記した）
- `approvalPolicy:"never"` + `sandbox:"read-only"`の組み合わせがCodex内部でどこまで保証されるかは、このリポジトリの外側（Codex CLI自体の実装）の話であり完全には検証できない。ただし、実際にプロンプトインジェクション文言を含む合成文字起こしで実機検証し、ファイル読み取り・コマンド実行が一切発生しないことを確認済み

## 3. 信頼性レビュー

**判定: SHIP**（P0・P1なし、P3×3を検出・一部修正）

検出事項:
- P3: Codex子プロセスの`stderr`ストリームに`'error'`リスナーが付いておらず、`stdin`/`stdout`と非対称だった → **修正済み**（`stderr`にも`'error'`リスナーを追加）
- P3: 起動タイムアウト時に失敗した子プロセスの後始末が行われず、次回再起動時に孤児プロセスとして残りうる → **修正済み**（起動失敗時にプロセスグループへ`SIGTERM`を送るよう修正）
- P3（情報提供）: 自動テストスイート（`companion:test`）に、共有マシンの負荷に起因するタイミング起因の間欠的失敗が残っている。`package.json`の`companion:test`へ`--test-concurrency=1`を追加し、各テストの待機時間（`waitFor`のタイムアウト値）を広げることで軽減したが、完全には解消しない。**これはこのマシン上で実行中の無関係な多数のプロセス（ChatGPT.appの各種ヘルパー、他プロジェクトの開発サーバー等、本セッションが起動したものではない）による負荷が原因であり、Phase 4のコード自体の欠陥ではない**（両レビュアーが実際にコードを読んで確認済み）。コミット時には実際にクリーンな実行結果（114/114）を得てから進めた。

## 7. 追加修正: 次回対応日反映バグ（2026-07-23）

実機確認で発見された「日付は分かるが時刻の言及が無い場合、次回対応日欄が反映されない」不具合の修正（`companion/src/analysis-prompt.ts`・`src/lib/analysis-datetime.ts`（新規）・`src/components/call-recorder.tsx`・`src/components/callflow-app.tsx`）に対し、同一の独立したOpusサブエージェント（Opus 4.8、`Agent(subagent_type: general-purpose, model: "opus")`）へ2回に分けてレビューを依頼した。

### 1回目のレビュー

**判定: REVISE**

検出事項:
- **P1×1**: 日付未入力の状態で時刻欄だけを入力すると、入力した時刻が即座に破棄される。日付・時刻を単一の`next_action_at`文字列から毎回分解し直す設計だったため、日付が空の状態では`combineDateTime`が`null`を返し、次の再描画で時刻inputの表示も巻き戻ってしまうことが原因。手動での次回対応日入力・解析結果レビュー画面の両方に影響する、本修正で新規に混入した回帰と判定
- P2×1: `companion/src/analysis-schema.ts`側の「日付のみ文字列を許容する」新しい挙動に対する自動テストが存在しない
- P3×2: 実在しない暦日（2026-02-30等）の直接テストが無い、`<input type="time">`のplaceholder属性が実質機能しない

### 修正対応

- `src/components/callflow-app.tsx`・`src/components/call-recorder.tsx`: 日付・時刻を単一の結合済み文字列から毎回分解する設計をやめ、日付欄・時刻欄をそれぞれ独立したstateとして保持する設計に変更。保存・反映時にのみ結合するようにした
- P2に対応し、新規`companion/src/analysis-schema.test.ts`（6件）を追加
- P3の`<input type="time">`のplaceholder属性を削除

### 2回目のレビュー

**判定: SHIP**（P0・P1なし）

1回目のP1バグが実際のデータフローの追跡により解消していることを確認。新たにP2×1（日付欄をクリアした際、時刻欄の表示が連動してクリアされない場合がある）を検出したが、実害は限定的（保存・反映される値自体は正しくnull/undefinedになる）と判断され、コミットをブロックするレベルではないとされた。この点も追加修正でコミット前に対応済み。

企業ID整合性チェック（`isSameCompany`）・プロンプトインジェクション対策（`analysis-prompt.ts`のBASE_INSTRUCTIONS）への悪影響が無いことも、いずれの回でも独立に再確認された。
