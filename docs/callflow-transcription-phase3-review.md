# Phase 3（ローカル文字起こし）レビュー記録

作成日: 2026-07-22
対象ブランチ: `feature/local-call-recorder-codex`

このセッションでは、Claude Code（Sonnet 5）が実装者として作業し、設計・実装のレビューには独立したClaude Codeサブエージェント（Agentツール、`subagent_type: general-purpose`、`model: "opus"`で起動。このセッションの実行環境では`model: "opus"`はOpus 4.8（`claude-opus-4-8`）に解決される）を、役割ごとに毎回新規のインスタンスとして使用した。

**補足（技術的な注記）**: 当初はプロジェクト固有の役割別サブエージェント定義（`.claude/agents/*.md`）を作成してレビューに使う計画だったが、実行中に「新規作成したプロジェクト定義は稼働中のセッションではホットリロードされない」という制約が判明した（`Agent`ツールが未知のサブエージェント種別としてエラーを返すことを実際に確認した）。そのため、役割ごとのレビュー観点・手順を`general-purpose`エージェントへのプロンプトに直接埋め込む形に切り替えた。エージェント自体は「このセッションの実装作業には一切関与していない、独立した新規インスタンス」であり、レビューの独立性という目的自体は損なわれていない。

---

## 1. 設計レビュー（Phase 3A/3B実装前、計画書に対して）

計画段階で実施。CORS（DELETEメソッドの許可漏れ）、ジョブ所有者確認の方式未定義、MVP音声長上限未定義の3点を指摘され、実装前に計画を修正した（詳細は実装差分に反映済み）。

## 2. Phase 3Aレビュー（環境構築・モデル取得・ベンチマークスクリプト）

- セキュリティレビュー: Pythonへの文字列補間によるコード注入パターン（P2）、シグナルハンドリングの不備（P3）を検出・修正
- 信頼性レビュー: モデルダウンロードのタイムアウト欠如（P1）、失敗時のエラー握りつぶし（P2）、`/usr/bin/time -l`でラップしたプロセスの孤児化バグ（P2、直接の子PIDだけをkillすると孫プロセスが生き残る）を検出・修正。孤児化バグは筆者（実装者）も独立に`/usr/bin/time -l sleep N &` + `pgrep`で再現・検証済み
- 再レビューで指摘ゼロ（SHIP-READY）を確認してから`chore: prepare local whisper transcription`としてコミット済み

## 3. Phase 3Bレビュー（本ドキュメントの主対象）

### 3.1 セキュリティレビュー（1回目）

対象: `companion/src/transcription-{config,process,jobs,routes}.ts`、関連する`cors.ts`/`server.ts`の差分、`src/lib/companion-client.ts`、`src/components/call-recorder.tsx`。

**判定: SHIP**（P0・P1なし）

検出事項:
- P2: アップロード受信中の件数が同時実行/待機上限の判定に含まれておらず、大量の同時リクエストで実質的な上限を回避できる
- P3×3: `temporaryFilesDeleted`の初期値誤り／GET・DELETEにPOSTと同様のOrigin明示検証が無い／ffmpeg完了直後のキャンセル競合で削除済みWAVに対しwhisper起動を試みうる

P0・P1が無かったため3回の修正ループは発生せず、指摘された4件（P2×1、P3×3）はいずれも軽微だったが、後続の信頼性レビュー前にまとめて修正した（品質向上のための任意対応。詳細は[callflow-transcription-security.md](./callflow-transcription-security.md)参照）。

### 3.2 信頼性レビュー

**判定: BLOCK**（P1×2を検出）。修正→再検証を実施。

- **P1-A**: `cancelJob()`で開始された非同期の後片付け（`finishJob`、一時ファイル削除＋完了ジョブTTLタイマー登録）が、`shutdown()`のタイマー一括クリアより後に完了するケースで、TTLタイマー（既定10分）が誰にもクリアされず残存する。レビュアーは実際に独立した再現スクリプトで`process.getActiveResourcesInfo()`に残存`Timeout`を確認し、`npm run companion:test`が実際に約10分間終了しないことも突き止めた。
  - 修正: 完了ジョブ用TTLタイマーを`.unref()`し、ハウスキーピング専用タイマーがプロセスの生存を左右しないようにした
- **P1-B**: `process()`内の一部のfs操作（`createTempFile`・`estimateWavDurationMs`）が`try/catch`で保護されておらず、例外が発生すると`void this.pump()`経由で未処理のPromise rejectionとなり、Node.js（v24）の既定動作でCompanionプロセス全体がクラッシュする。文字起こし中のジョブだけでなく、その時点で進行中の他の`/v1/audio`アップロードも巻き添えになる
  - 修正: `process()`全体を`try/catch`で包み、想定外の例外はそのジョブを`internal_error`として終了させるだけに限定した

再検証: 修正後、`npm run companion:build`（tsc）成功、`npm run companion:test`が実測約3秒・80/80件成功・プロセスも正常終了することを確認（修正前は同じテストスイートが完了せず、10分規模でハングしていたことを筆者も実際に観測している）。

### 3.3 最終ゲートレビュー（Opus、新規インスタンス）

セキュリティレビュー・信頼性レビューのいずれにも関与していない、完全に新規のOpusインスタンスが、完成した差分全体（変更ファイル5件・新規ファイル11件）を最初から独立に精査した。事前レビューの記載内容（「修正済み」「SHIP」等）は鵜呑みにせず、実際のコードを読んで裏付けを取る指示のもとで実施。

**判定: SHIP**（P0・P1なし）

自ら実行して確認した内容:
- `npm run companion:build`（tsc）: クリーン
- `npm run companion:test`: 80/80件成功、約3秒で正常終了（過去に発生した約10分間のハングは再発しないことを確認）
- `npm test`（メイン画面側）: 129/129件成功
- `npm run lint`: 警告1件のみ（この差分に含まれない既存ファイルの未使用変数、無関係）
- `npm run build`（next build）: 成功
- `git diff --check`: クリーン
- `git status`: モデル・証明書・実音声・トークン等の混入なし

信頼性レビューで検出された2件のP1（TTLタイマーのイベントループ引き止め、fs例外による未処理rejection）について、「その場しのぎの修正で別の形で問題が残っていないか」を独立に追跡し、いずれも構造的に解消されていることを確認（`ttl.unref()`はタイマーがプロセス生存の唯一の理由になることを構造的に防ぐため、レース条件の発生有無に関わらず安全。`process()`全体を包む`try/catch`と、`deleteTempFile`自体が例外を投げない実装の組み合わせにより、fs例外が他のジョブ・他の`/v1/audio`アップロードへ波及する経路が無いことを確認）。

検出事項（いずれもP3、非ブロッキング）:
- 同時実行数0（アイドル時）に複数リクエストが同時到達すると、`queue`が瞬間的に`maxQueuedJobs`を超えうる（`pump()`が1件ずつ捌くまでの間）。単一利用者のローカルツールであり、既にペアリング済みトークンを持つ主体のみが到達できる操作のため実害は軽微
- `CompanionErrorCode`に`internal_error`が定義されておらず`"unknown"`にフォールバックしていた点（UI表示上はサーバーが返す`message`をそのまま表示するため無害）。**このレビュー後に修正済み**（`src/lib/companion-client.ts`に`internal_error`を追加）

スコープ規律（Codex解析・架電結果自動入力・Supabase保存が混入していないこと）、フロントエンド⇔バックエンドの契約一致（状態遷移・エラーコード・フィールド名）も含めて独立に確認し、いずれも問題なし。
